Sección 01 — Visión general

Resumen del proyecto

Elemental Battlecards es un videojuego de cartas por turnos que enfrenta a un jugador contra un bot con 10 niveles de dificultad o contra otro jugador en la misma red local (LAN). Se compone de dos aplicaciones que comparten repositorio.

Cliente

Frontend / Frontend/

Juego desarrollado con Phaser 3.90 y empaquetado con Vite. Incluye 19 escenas: login, registro, menú principal, selección de dificultad, perfil, misiones, logros, colección de cartas y la escena de juego con la IA del bot.

Servidor

Backend / Backend/

API construida con Node.js, Express y Socket.io en el puerto 3001. Gestiona autenticación con JWT, perfil de jugador, progreso persistente y las salas multijugador en tiempo real.

Persistencia

Base de datos PostgreSQL

PostgreSQL 18 con base elemental: 10 tablas, 4 vistas, 2 procedimientos almacenados, 1 trigger y 77 restricciones que sostienen la integridad (ACID) del sistema.

Orientación a objetos

POO aplicada en ambos lados

Clases como Card, Deck, Player, TurnManager (frontend) y AuthService, RoomManager, SocketGateway (backend) encapsulan estado y comportamiento.

Principios de diseño

SOLID como regla obligatoria

Dependencias por interfaces inyectadas en el constructor, contratos verificados al arrancar, responsabilidad única por clase y sustitución de Liskov garantizada (ver sección 4).

Separación de capas

Dominio desacoplado

Las entidades del dominio no se conectan directamente a Phaser ni a Sequelize: las escenas solo presentan, los servicios deciden y los repositorios son el único puente con el ORM.

Sección 02 — Reglas del juego

Mecánicas del juego

El juego combina teoría de conjuntos (los 6 tipos elementales como universo), ventajas elementales, fusión de cartas idénticas y un flujo de turnos estricto con turnos obligatorios de ataque.

Los 6 elementos y sus ciclos de ventaja

Fuego → vence a → Planta → vence a → Agua → vence a → Fuego
Luz → vence a → Sombra → vence a → Espíritu → vence a → Luz

Definido en Frontend/src/helpers/constants.js mediante el mapa ADVANTAGES.

Reglas centrales de la partida

ReglaDetalleConfiguración
Mazo inicial48 cartas: 8 copias de cada uno de los 6 tipos (solo nivel 1), barajadas con el algoritmo Fisher-Yates.INITIAL_DECK_SIZE = 48
ManoSe inicia con 4 cartas; máximo de 4 en mano.MAX_HAND_SIZE = 4
Campo de batalla6 espacios donde se juegan las cartas.MAX_FIELD_SIZE = 6
CombateResuelto por resolveCombat(): diferencia de 2+ niveles = victoria automática; 1 de diferencia anula (no) la ventaja de tipo; mismo nivel decide la ventaja elemental; si no hay ventaja → empate.helpers/combat.js
FusiónDos cartas del mismo tipo y nivel se fusionan en la carta del nivel superior (I+II → III). La carta de nivel III no se puede fusionar.player.fuseCards()
CementerioAl destruir una carta de nivel 2 o 3, se descompone en 2^(nivel-1) cartas base del mismo tipo. Si el mazo se agota, se baraja el cementerio al mazo.addCardDataToGraveyard()
Ataque obligatorioTras 3 turnos sin atacar, el jugador está obligado a atacar.MANDATORY_ATTACK_TURN = 3

Tiempo por turnoCada turno tiene 12 segundos (también en LAN).TURN_TIME_LIMIT_MS = 12000
EsenciaRellenar las 6 esencias (una por elemento) activa los orbes elementales y es condición de victoria.EssenceManager

Condiciones de victoria

Evalúa VictoryEvaluator (lógica pura, sin Phaser), en este orden:

  • Victoria del oponente por inactividad del jugador (3 turnos).
  • Control de campo: tener 6 tipos elementales distintos en el campo.
  • Llenar las 6 esencias elementales.

Muy fácil … Mito (IA)

El bot depende de la dificultad elegida: probabilidad de fusión, umbral de ataque, retraso entre acciones y bonificador de puntuación de ataque.

Nivel 6-10: Experto, Maestro, Gran Maestro, Leyenda y Mito — con retrasos de hasta 0 ms (decisiones instantáneas) y thresholds de ataque negativos que lo hacen agresivamente preciso.

Sección 03 — Cliente

Frontend · Phaser 3

El cliente es un juego Phaser 3.90 de 1600×1000 en modo Scale.FIT con contenedor DOM para los formularios de login y menús. El orden de escenas se define en Frontend/src/main.js.

Carga

Boot & Preloader

bootScene carga los assets mínimos de la pantalla de carga y Preloader carga el resto: imágenes de cartas, videos de fondo, íconos y audio.

Cuentas

Login & registro

Pantallas de autenticación contra /api/auth. Si no hay token, el juego entra en modo offline sin romper la interfaz.

Menú

Home & navegación

Menú principal, ajustes, estadísticas, niveles de dificultad, perfil, misiones, colección, mecánicas y pantalla

Acción

GameScene

La escena central (~2000 líneas) orquesta la partida contra el bot: robo de cartas, arrastre, fusión, combate animado, turnos y fin de partida.

UI paralela

uiScene

Se ejecuta en paralelo a la escena de juego: botón hamburguesa ☰, menú de pausa estilizado (continuar / reiniciar / configuración / salir), HUD de orbes.

Multijugador

GameSceneLAN

Variante sincronizada de la partida: el cliente LAN conecta por socket.io-client y replica las acciones de ambos jugadores en tiempo real.

Objetos del dominio del juego

Card / game_objects/card.js

Representa una carta con tipo, nivel e identificador único de instancia (instanceId) que permite rastrearla a lo largo de todo su ciclo de vida.

CardDefinitions / card-definitions.js

Catálogo generado programáticamente de las 18 cartas (6 tipos × 3 niveles) con IDs tipo-nivel. Generado a partir de la plantilla tipo × nivel para evitar errores.

Deck / deck.js

Gestiona el mazo y cementerio: crea las 48 cartas (Regla #7: 8 copias por tipo), baraja con Fisher-Yates y permite robar.

Player / player.js

Estado completo del jugador: mazo, mano, campo (6 slots), cementerio y esencias. Implementa jugar carta, fusionar campo+campo y mano+campo.

TurnManager / game/TurnManager.js

Lógica pura del flujo de turnos: estado, contadores de inactividad, ataques obligatorios y bloqueos por animación. No depende de Phaser.

BotAI / game/BotAI.js

IA del oponente con parámetros por dificultad: fusión, thresholds de ataque, retardos y bonus estratégico.

Decisión de diseño. Los objetos del dominio (Player, TurnManager, VictoryEvaluator) son lógica pura: no conocen Phaser ni Sequelize. La escena consulta sus estados y se encarga solo de dibujar y coordinar (principio de responsabilidad única y capas).

Resolver el combate — helpers/combat.js

export function resolveCombat(attacker, defender) {
    const levelDiff = attacker.level - defender.level;

    // Regla: diferencia de 2 niveles o más es victoria automática.
    if (levelDiff >= 2) return { winner: 'attacker', loser: 'defender' };
    if (levelDiff <= -2) return { winner: 'defender', loser: 'attacker' };

    if (levelDiff === 1) {
        // 1 de nivel: si el defensor tenía ventaja de tipo, se vuelve neutral.
        if (defenderAdvantage === attacker.type) return { winner: 'none', loser: 'none' };
        return { winner: 'attacker', loser: 'defender' };
    }
    // Mismo nivel → decide la ventaja de tipo (ADVANTAGES en constants.js).
    if (attackerAdvantage === defender.type) return { winner: 'attacker', loser: 'defender' };
    ...
}
Sección 04 — Servidor

Backend · Node.js

API REST + tiempo real en el puerto 3001, construida por capas con inyección de dependencias estricta. El arranque es un composition root: server.js es un wrapper fino de Backend/src/bootstrap.js.

Proceso

Orden de arranque

dotenv → AppConfig/Logger → DatabaseFactory crea Sequelize → DatabaseInitializer conecta y sincroniza → routers de auth → AppFactory crea Express → socket.io → SocketGateway registra eventos → listen.

Fallos degranada

Tolerancia a fallos

Si la BD no conecta, el servidor no se cae: marca databaseAvailable=false y desmonta las rutas de login/perfil (modo LAN). El juego y las salas socket siguen funcionando.

Contratos

DI estricta

Las clases dependen de interfaces (IUserRepository, IPasswordHasher, ITokenService, IRoomStore) validadas con assertContract al arrancar (fail-fast).

Arquitectura por capas

Conocimiento real, no solo el esquema

  • Login con username (no email); registro usa email + hash bcrypt.
  • JWT firmado con secreto configurable; expiración vía variable de entorno.
  • CORS abierto (*) por configuración, necesario para las partidas LAN.
  • Los error de la BD suben hasta errorHandler → HTTP 500 con { message }, jamás una respuesta inventada.

Identidad

users

Cuentas de jugador: username único (login), email único, contraseña con hash bcrypt. Home de todas las relaciones 1:N.

Catálogos

cards · missions · achievements

18 cartas (6 tipos × 3 niveles, UNIQUE tipo+nivel), 6 misiones con recompensa en gemas y 6 logros. Sembrados con ON CONFLICT DO NOTHING.

Estado 1:1

player_stats

Partidas, victorias, derrotas, racha actual, mejor racha y gemas. La crea y mantiene el trigger, nunca un INSERT manual de la app.

Historial

battles

Resultado (victoria/derrota), oponente (bot/lan), dificultad y nivel 3 en campo. Cada INSERT dispara el trigger de stats.

Progreso N:1

player_cards / player_missions / player_achievements

Colección, progreso de misiones y logros desbloqueados. Claves compuestas: un jugador no repite carta/misión/logro.

Historial

Tipos elementales con los que cada jugador ha atacado (dominio validado por CHECK del motor).

Gestión del esquema. Dos mecanismos complementarios: sequelize.sync({ alter: true }) alinea modelos↔tablas en cada arranque, y los scripts SQL (schema.sql → vistas.sql → triggers.sql → procedimientos.sql → datos_demo.sql) definen el esquema completo + objetos programados + datos demo. Advertencia documentada: sync({alter:true}) puede eliminar los DEFAULT now(); por eso schema.sql los restaura con ALTER TABLE ... SET DEFAULT (reparación idempotente).

Datos demo: 4 usuarios demo_kai, demo_luna, demo_ryo, demo_zara (contraseña demo1234), 18 batallas insertadas en orden cronológico para que el trigger derive rachas correctamente, colección y progreso de misiones.

Sección 06 — Teoría aplicada

ACID y CAP

ACID gobierna lo que pasa dentro de una transacción; CAP decide qué se sacrifica entre nodos cuando la infraestructura falla. El proyecto demuestra ambos con objetos reales y demos reproducibles en psql.

A · Atomicidad — "todo o nada"

  • El DDL + seeds de schema.sql van dentro de BEGIN; ... COMMIT;.
  • Cada CALL a un procedimiento corre en una transacción implícita: sp_registrar_batalla escribe battles y player_attack_types.
  • El INSERT de batalla + la actualización del trigger son inseparables.
  • Demo: un CALL ... 'tierra' (elemento inválido) inserta la batalla y luego falla el CHECK → la batalla ya insertada se revierte (contador de battles no cambia).

C · Consistencia — "invariantes válidos"

  • 77 restricciones: PK, FK con CASCADE, CHECK de dominio (result, element, level, opponent), UNIQUE y NOT NULL.
  • El trigger mantiene battles_played = battles_won + battles_lost.
  • El servicio valida el mismo dominio como primera barrera.
  • Demo: INSERT ... user_id 99999 → falla la FK; result 'empate' → falla el CHECK; todo ROLLBACK sin dejar rastro.

I · Aislamiento — "no se pisan"

  • Nivel del servidor: READ COMMITTED (default de PostgreSQL).
  • Dos jugadores terminan partidas a la vez: cada POST es una transacción y cada uno escribe su propia fila de player_stats (PK user_id) → sin carrera.
  • Demo: SHOW transaction_isolation; → read committed.

D · Durabilidad — "sobrevive a caídas"

  • PostgreSQL escribe en el WAL y confirma con fsync antes de responder.
  • synchronous_commit = on: consistente en disco al confirmar.
  • Demo: SHOW synchronous_commit; → on y SELECT pg_current_wal_lsn();.

CAP — nuestra postura: CP

El sistema sí es distribuido (clientes en red + servidor + BD), aunque el despliegue sea de un nodo por capa. Como la red es falible, P es obligatoria; la decisión real es C o A ante una partición. Este proyecto elige Consistencia > Disponibilidad:

SituaciónQué hace el sistemaPropiedad cedida
La BD no responde al arrancarbootstrap.js → databaseAvailable=false; no se montan rutas de datos (modo LAN)A
Error de BD en una peticiónerrorHandler → HTTP 500; jamás una respuesta inventada o cacheadaA
Escrituras en Postgressiempre contra el primario (single-writer); sin primario, no hay escrituraA en partición
Login / registros / rankingsnecesitan SIEMPRE el dato más reciente (credenciales, únicos)eligen C
Escrituras en Postgres→ síncronas, nunca se acepta escritura divergente (evita split-brain)—

La evidencia en el código

// Backend/src/bootstrap.js
} catch (error) {
  logger.error('No se pudo conectar a la BD:', error.message);
  databaseAvailable = false;  // la BD manda
}
if (!(config.dbEnabled && databaseAvailable)) {

¿Y la disponibilidad (A)?

  • El juego LAN / salas (RoomManager en memoria) no depende de la BD: las partidas siguen aunque la BD esté caída.
  • El frontend sin sesión entra en modo offline en vez de romper la UI.
  • Es una partición deliberada: cuentas y progreso = CP; relato de juego = disponible.
  • PACELC: incluso sin partición se elige C sobre latencia (synchronous_commit=on).
Frase de cierre. "ACID gobierna lo que pasa dentro de la base; CAP gobierna qué pasa cuando la infraestructura falla. Nuestro sistema aplica ACID completo en el nodo de PostgreSQL y adopta la postura CP de Brewer ante caídas: nunca servir datos viejos o incompletos."
Sección 07 — Objetos programados

Vistas · Procedimientos · Trigger

Tres tipos de objetos SQL encapsulan consultas y reglas en el propio motor. Las vistas no duplican datos (se calculan al consultar, siempre frescas); los procedimientos escriben varias tablas en una transacción; el trigger mantiene derivados automáticos.

Las 4 vistas Backend/sql/vistas.sql

VistaResuelveTécnicas SQL
v_ranking_jugadoresRanking: partidas, victorias, % de victoria, rachas y gemas. Incluye jugadores sin stats (demuestra el LEFT JOIN).LEFT JOIN + CASE + COALESCE
v_coleccion_cartasCuántos jugadores poseen cada carta y su porcentaje.LEFT JOIN + COUNT + NULLIF (÷0)

Los 2 procedimientos almacenados Backend/sql/procedimientos.sql

sp_registrar_batalla (user, resultado, oponente, dificultad, nivel3, elemento)

  • Valida dominio (resultado, oponente, existencia del usuario) → RAISE EXCEPTION si falla.
  • INSERT en battles (RETURNING id).
  • INSERT en player_attack_types si se informa el elemento (CHECK valida).
  • RAISE NOTICE con las stats que el trigger ya actualizó.

La validación del elemento se deja a propósito en el CHECK: si es inválido, la transacción se revierte tras insertar la batalla → demo viva de atomicidad.

sp_completar_mision (user, misión)

  • Valida que existan misión y usuario.
  • UPSERT en player_missions: progress = target, completed = true.
  • UPSERT en player_stats: gems += reward_gems (misma transacción).
  • RAISE NOTICE con el total de gemas.

Si la 2ª escritura fallara, la 1ª se revierte: no existe misión completada sin pago.

-- OJO: CALL no acepta subconsultas (limitación de PostgreSQL) → variables psql con \gset
SELECT id AS kai FROM users WHERE username = 'demo_kai' \gset
CALL sp_registrar_batalla(:kai, 'victoria', 'bot', '5', false, 'agua');
-- NOTICE: Batalla #25 registrada ... partidas=7 (V:6 D:1) | racha=3 | gemas=350
-- Caso de error (atomicidad):
CALL sp_registrar_batalla(:kai, 'victoria', 'bot', '5', false, 'tierra');  -- se revierte todo

El trigger Backend/sql/triggers.sql

trg_stats_batalla — AFTER INSERT ON battles FOR EACH ROW → función fn_actualizar_stats_batalla():

INSERT en battles ──▶ trigger ──▶ UPSERT en player_stats • battles_played +1 · battles_won/lost +1 según result · racha +1/0 · mejor racha con GREATEST · updated_at = now() · crea la fila si no existe

Por qué existe

Las stats son un dato derivado del historial de battles. El trigger las mantiene de forma automática, atómica y sin posibilidad de desincronización: no hay código de aplicación que pueda olvidarse de actualizarlas.

Por qué las gemas NO están en el trigger

Pagar recompensas es regla de negocio con validación y dos escrituras → pertenece a sp_completar_mision (fallas controladas), no a un reflejo automático oculto. ProfileService.recordBattle() no escribe stats: única fuente de verdad = el trigger.

Demo de trigger. Dentro de transacción para no ensuciar la base:
BEGIN; INSERT INTO battles (user_id, result, opponent, difficulty) VALUES (:kai,'victoria','bot','5'); SELECT battles_played, current_streak FROM player_stats WHERE user_id = :kai; ROLLBACK;
Sección 08 — Multijugador

Juego en red (LAN)

Dos jugadores en la misma red local se enfrentan en tiempo real. El backend solo hace de relay (sin lógica de juego): las salas viven en memoria y cada acción se sincroniza entre clientes.

Salas

Código de 6 dígitos

RoomCodeGenerator genera códigos numéricos; RoomManager crea/unirse salas de 2 jugadores e inicia la partida. Estado en memoria: se reinicia con el servidor.

Evento

game_event

El SocketGateway reenvía los eventos de juego entre los dos clientes de la sala. El host siempre juega primero.

Sincronización

12 s por turno

El turno se limita a 12 segundos y las acciones (jugar, atacar, fusionar) se replican casi en tiempo real en ambos clientes.

Flujo típico

  1. Anfitrión: en el menú principal elige "Juego en red (LAN)" → Crear sala → el servidor responde el código.
  2. Invitado: abre http://[IP_DEL_ANFITRION]:5173 → "Unirse a sala" → ingresa el código de 6 dígitos.
  3. Al completarse la sala, ambos clientes reciben la señal y se abre GameSceneLAN.
  4. El host juega el primer turno; las acciones se envían como game_event y se replican al oponente.

Conexión: el cliente usa socket.io-client y se conecta al backend en el puerto 3001. La autenticación JWT y el juego están desconectados a propósito: se puede jugar en LAN incluso sin cuenta (modo offline de profileApi.js).

Sección 09 — Puesta en marcha

Cómo ejecutar el proyecto

El arranque requiere dos procesos: el backend primero (expone la API y socket.io) y el frontend después (sirve el juego con Vite).

1 · Backend (puerto 3001)

cd Backend
npm install
npm run dev        # nodemon server.js
# escucha en 0.0.0.0:3001

2 · Frontend (Vite)

cd Frontend
npm install
npm run dev        # vite --host
# abre la URL local/network que imprime

Base de datos

PostgreSQL 18 con la base elemental, datos demo y objetos programados cargados con:
schema.sql → vistas → triggers → procedimientos → datos_demo.sql (idempotentes).

Variables de entorno

Backend/.env define puerto, dialecto (DB_USE_SQLITE=false para Postgres), secreto JWT y CORS. La conexión psql:
PGPASSWORD=123456 psql -U postgres -h 127.0.0.1 -d elemental

Modo SQLite alternativo

Con DB_USE_SQLITE=true el backend usa un archivo database.sqlite (CAP trivial); el esquema y script funcionan igual, aunque SQLite no soporta procedimientos almacenados.

Problemas conocidos documentados. column ... has no default value → re-ejecutar schema.sql; CALL no acepta subconsultas → variables \gset; EADDRINUSE :3001 → ya hay un backend activo; doble conteo de stats → resuelto: la única fuente es el trigger.
Sección 10 — Cierre

Conclusiones y respaldo

El proyecto integra un juego funcional (POO + Phaser), un servidor por capas con SOLID e inyección de dependencias, y una base de datos relacional con objetos programados que demuestran teoría real: ACID completo y postura CP ante caídas.

Disciplina técnica

POO y SOLID aplicados en ambas aplicaciones; contratos verificados al arrancar (assertContract); dominio desacoplado de Phaser y de Sequelize; composición sobre herencia.

Integridad de datos

77 restricciones, trigger que mantiene derivados, procedimientos transaccionales y vistas siempre frescas: el motor rechaza datos ilegales aunque el código de aplicación tenga un bug.

Funcionalidad real

Multijugador LAN con socket.io, IA con 10 dificultades, misiones, logros, colección de cartas, ranking y progreso persistente por jugador.
