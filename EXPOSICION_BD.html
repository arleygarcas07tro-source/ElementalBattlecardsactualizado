01 — Arquitectura

¿Dónde vive la base de datos?

Tres capas conectadas por HTTP y Sequelize. La BD está desacoplada: las escenas de Phaser jamás tocan SQL; el repositorio es el único puente con el ORM.

┌─────────────────────────────┐
│  FRONTEND (Phaser 3 + Vite)  │  escenas: login, perfil, misiones…
│  src/helpers/profileApi.js   │  fetch + Authorization: Bearer <jwt>
└──────────────┬──────────────┘
               │ HTTP / fetch
┌──────────────▼──────────────┐
│  BACKEND (Express :3001)     │  /api/auth · /api/profile
│  middleware JWT → controller → service → repository
└──────────────┬──────────────┘
               │ Sequelize (ORM)
┌──────────────▼──────────────┐
│  POSTGRESQL 18 :5432 — "elemental"  │  10 tablas · 1 vista
│  1 procedimiento · 1 trigger       │  WAL + synchronous_commit=on
└─────────────────────────────┘

Arranque del backend

  1. dotenv carga .env → AppConfig.
  2. DatabaseFactory crea Sequelize según DB_USE_SQLITE=false → dialecto postgres.
  3. DatabaseInitializer.connect() → authenticate. Si falla: databaseAvailable=false, el servidor no se cae.
  4. sync({ alter: true }) alinea modelos ↔ tablas.
  5. Se montan routers (solo si hay BD) y se hace listen.

Regla de diseño

  • La lógica de negocio vive en el servicio.
  • Las escenas solo presentan.
  • El repositorio es el único que habla con Sequelize.
  • El motor aporta restricciones, trigger, vista y procedimiento.
  • Contratos por interfaz verificados con assertContract (Liskov / ISP).

Las 77 restricciones: el andamiaje de integridad

Todas las columnas obligatorias con valores por defecto donde corresponde.

03 — ACID · A

Atomicidad — "todo o nada"

A

Una transacción con varias escrituras se aplica completa o se revierte completa; nunca queda a medias.

Dónde está en el proyecto

  • El DDL + seeds de schema.sql van en BEGIN; … COMMIT;.
  • Cada CALL es una transacción implícita con 2+ escrituras.
  • sp_completar_mision escribe player_missions + player_stats.
  • INSERT de batalla + actualización del trigger: inseparables.
-- El INSERT del historial y el UPDATE del trigger van juntos:
-- si la 2ª sentencia falla, la 1ª también se revierte
BEGIN;
INSERT INTO battles (user_id, result)
  VALUES (:kai, 'victoria');   -- el trigger suma +1 en player_stats
INSERT INTO battles (user_id, result)
  VALUES (99999, 'victoria');   -- ✗ FK: usuario inexistente
COMMIT;

SELECT count(*) AS despues FROM battles;                       -- ¡igual! se revirtió todo
SELECT battles_played FROM player_stats WHERE user_id = :kai;  -- ¡igual! el trigger también
Frase clave: "la batalla ya estaba escrita en memoria cuando falló la 2ª sentencia; PostgreSQL revirtió la transacción completa: 0 filas persistidas — ni la batalla ni la actualización del trigger."
03 — ACID · C

Consistencia — "los invariantes nunca se rompen"

C

Cada escritura deja la BD en un estado válido según todas las reglas declarativas y de dominio.

Evidencias

  • 77 restricciones (PK/FK/CHECK/UNIQUE/NOT NULL).
  • Catálogos con ON CONFLICT DO NOTHING → re-ejecución sin duplicados.
  • Validación de dominio también en el servicio (ValidationError).
  • Trigger que mantiene partidas = V + D.
  • Hash bcrypt de contraseñas.
-- Fuerza bruta contra los invariantes (fallan)
BEGIN;
INSERT INTO battles (user_id, result)
VALUES (99999, 'victoria');   -- ✗ FK: usuario inexistente
ROLLBACK;

BEGIN;
INSERT INTO battles (user_id, result)
VALUES (:kai, 'empate');        -- ✗ CHECK: fuera de dominio
ROLLBACK;

-- La BD rechaza los datos inválidos aunque nadie valide en JS.
03 — ACID · I

Aislamiento — "las transacciones concurrentes no se pisan"

I

Transacciones simultáneas no ven los datos a medias de otras; el resultado equivale a ejecutarlas una tras otra.

En el proyecto

  • Nivel del servidor: READ COMMITTED (default de PostgreSQL).
  • Dos jugadores terminan partidas a la vez: cada POST es una transacción sobre su propia fila de player_stats (PK user_id → sin carrera).
  • El UNIQUE de username rechaza registros simultáneos duplicados al confirmar.
SHOW transaction_isolation;
-- read committed

-- Demostración en serio: dos ventanas de psql,
-- una escribe sin confirmar y la otra no la ve
-- hasta el COMMIT.
TV1> BEGIN; UPDATE player_stats SET gems = gems + 50 WHERE user_id = 1;
TV2> SELECT gems FROM player_stats WHERE user_id = 1;  -- no ve el cambio
TV1> COMMIT;
03 — ACID · D

Durabilidad — "un COMMIT confirmado sobrevive a caídas"

D

Una vez respondido "commit OK", el dato no se pierde ni con un corte de energía.

Cómo lo garantiza PostgreSQL

  • Cada transacción se registra en el WAL (Write-Ahead Log).
  • Se confirma con fsync antes de responder al cliente.
  • synchronous_commit = on → consistente en disco al confirmar.
Traducción al juego: si confirmaste una victoria y se fue la luz, la victoria y sus gemas siguen ahí al reconectar.
SHOW synchronous_commit;   -- on
SELECT pg_current_wal_lsn();  -- posición actual del WAL

-- Resumen ACID en una frase:
· atomicidad en cada CALL y en cada INSERT+trigger;
· consistencia en 77 restricciones + el trigger;
· aislamiento READ COMMITTED entre jugadores;
· durabilidad con WAL + synchronous_commit.
04 — Teorema CAP

CAP — ¿qué pasa cuando la red falla?

En un sistema distribuido solo se garantizan 2 de 3: Consistencia, Adisponibilidad y P tolerancia a partición. Como la red es falible, P es obligatoria → la decisión real es C o A.

[Clientes Phaser en la red]  ←── partición →─  [Express :3001]  ←─┐
                                                               │ partición
                                                   [PostgreSQL :5432] ←┘

Nuestra decisión: CP 🔒

  • BD no responde al arrancar → databaseAvailable=false, no se montan rutas de datos (modo LAN). → cede A
  • Error de BD en petición → HTTP 500, jamás una respuesta cacheada o inventada. → cede A
  • Escrituras siempre contra el primario (sin primario, no hay escritura). → cede A
  • Login y rankings necesitan SIEMPRE el dato más reciente → elijo C.

La evidencia no es teoría

// Backend/src/bootstrap.js
} catch (error) {
  logger.error('No se pudo conectar a la BD:', error.message);
  databaseAvailable = false;   // la BD manda
}
if (!(config.dbEnabled && databaseAvailable)) {
  return disabled;   // se desmontan, no se sirve stale
}
Pregunta clásica: ¿ACID y CAP no chocan? No: ACID es la semántica dentro del nodo; CAP es el trade-off entre nodos cuando hay partición. PG da ACID local y es CP en distribución.
04 — CAP aplicado

¿Entonces dónde queda la disponibilidad?

Plano de juego: disponible

  • El relay de socket.io (RoomManager, en memoria) no depende de la BD → las partidas LAN siguen con la BD caída.
  • El frontend sin sesión entra en modo offline (no-op) en vez de romper la UI.

Partición deliberada del sistema: cuentas y progreso = CP; partida = disponible.

PostgreSQL en producción

  • Con streaming replication + failover, PG es CP: el primario es única fuente de verdad; un secundario aislado no acepta escrituras (sin split-brain).
  • Sin réplicas: toda lectura va al primario → consistencia fuerte.
  • PACELC: incluso en operación normal elegimos C sobre latencia (synchronous_commit=on).

Contraste SQLite (DatabaseFactory)

  • Un archivo local, mismo proceso → sin red = CAP trivial (CP por construcción).
  • El dialecto lo decide .env; esquema y scripts funcionan igual.
  • Limitación: sin procedimientos almacenados (vista y trigger sí existen).

Frase de cierre

"ACID gobierna lo que pasa dentro de la base; CAP gobierna qué pasa cuando la infraestructura falla. Nuestro sistema aplica ACID completo en el nodo de PostgreSQL y adopta la postura CP de Brewer ante caídas: nunca servir datos viejos o incompletos."

05 — Objetos programados · Vista

La vista — v_historial_batallas

Historial legible: muestra el username en lugar del id, en orden cronológico inverso. Backend/sql/vistas.sql

DROP VIEW IF EXISTS v_historial_batallas;

CREATE VIEW v_historial_batallas AS
SELECT
    b.id,
    u.username,
    b.result,
    b.opponent,
    b.difficulty,
    b.level3_on_field,
    b.created_at
FROM battles b
JOIN users u ON u.id = b.user_id
ORDER BY b.created_at DESC, b.id DESC;
Claves: JOIN (no LEFT) porque toda batalla tiene usuario garantizado por la FK; ORDER BY created_at DESC deja lo más reciente arriba.
05 — Objetos programados

El procedimiento almacenado

Se ejecuta con CALL. Corre en una transacción implícita: o se aplican todos los pasos o ninguno (atomicidad ACID).

sp_completar_mision (user, misión)

  1. Valida que existan misión y usuario → RAISE EXCEPTION.
  2. UPSERT en player_missions → progress = target, completed = true.
  3. UPSERT en player_stats → gems += reward_gems. Misma transacción.
  4. RAISE NOTICE con el total de gemas.
-- OJO: CALL no acepta subconsultas (limitación de PG) → variables con \gset
SELECT id AS ryo FROM users WHERE username = 'demo_ryo' \gset
CALL sp_completar_mision(:ryo, 'coleccionista');
-- NOTICE: Misión "Coleccionista" ... +100 gemas | total de gemas = 150
Clímax de atomicidad: las dos escrituras (progreso + gemas) son inseparables: si la 2ª fallara, la 1ª se revierte → el jugador no queda con misión completada sin cobrar (ni al revés).
05 — Objetos programados · Procedimiento

El procedimiento — sp_completar_mision

Marca una misión como completada y acredita la recompensa de gemas en la misma transacción. Backend/sql/procedimientos.sql

DROP PROCEDURE IF EXISTS sp_completar_mision(INTEGER, VARCHAR);

CREATE PROCEDURE sp_completar_mision(
    p_user_id    INTEGER,
    p_mission_id VARCHAR
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_mision missions%ROWTYPE;
    v_gemas  INTEGER;
BEGIN
    -- ===== Validaciones (antes de escribir) =====
    SELECT * INTO v_mision FROM missions WHERE id = p_mission_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'La misión "%" no existe', p_mission_id;
    END IF;

    IF NOT EXISTS (SELECT 1 FROM users WHERE id = p_user_id) THEN
        RAISE EXCEPTION 'El usuario con id % no existe', p_user_id;
    END IF;

    -- ===== Escritura 1: progreso de la misión =====
    INSERT INTO player_missions (user_id, mission_id, progress, completed, completed_at)
    VALUES (p_user_id, p_mission_id, v_mision.target, TRUE, now())
    ON CONFLICT (user_id, mission_id) DO UPDATE SET
        progress     = v_mision.target,
        completed    = TRUE,
        completed_at = COALESCE(player_missions.completed_at, now());

    -- ===== Escritura 2: recompensa en gemas =====
    INSERT INTO player_stats (user_id, gems, updated_at)
    VALUES (p_user_id, v_mision.reward_gems, now())
    ON CONFLICT (user_id) DO UPDATE SET
        gems       = player_stats.gems + v_mision.reward_gems,
        updated_at = now();

    SELECT gems INTO v_gemas FROM player_stats WHERE user_id = p_user_id;

    RAISE NOTICE 'Misión "%" completada: +% gemas | total = %',
        v_mision.title, v_mision.reward_gems, v_gemas;
END;
$$;
Atomicidad: dos UPSERT (progreso + gemas) en la misma transacción: o se aplican ambos o ninguno. COALESCE conserva la fecha de la primera vez que se completó.
05 — Objetos programados

El trigger

trg_stats_batalla — AFTER INSERT ON battles FOR EACH ROW → función fn_actualizar_stats_batalla(). Script: Backend/sql/triggers.sql.

INSERT en battles ──▶ trigger ──▶ UPSERT en player_stats
   • battles_played  +1
   • battles_lost/won +1 según result
   • current_streak  = racha +1 (victoria) / 0 (derrota)
   • longest_streak  = GREATEST(máximo histórico, racha actual)
   • updated_at      = now()
   • si el jugador no tenía fila, la crea

Por qué existe

Las stats son un dato derivado del historial de battles. El trigger las mantiene de forma automática, atómica y sin posibilidad de desincronización — no hay código de aplicación que pueda olvidarse de actualizarlas.

Por qué las gemas NO están en el trigger

Pagar recompensas es regla de negocio con validación y dos escrituras → pertenece a sp_completar_mision (fallas controladas), no a un reflejo automático oculto.

Dato verificado por integración: ProfileService.recordBattle() no escribe stats (3 batallas → pj=3, V=2, D=1, racha=1). Fuente única de verdad = el trigger.
Demo: BEGIN; INSERT INTO battles (user_id, result, opponent, difficulty) VALUES (:kai,'victoria','bot','5'); SELECT battles_played, current_streak FROM player_stats WHERE user_id = :kai; ROLLBACK;
05 — Objetos programados · Trigger

Trigger — trg_stats_batalla

AFTER INSERT ON battles FOR EACH ROW → ejecuta fn_actualizar_stats_batalla(). Backend/sql/triggers.sql

DROP TRIGGER IF EXISTS trg_stats_batalla ON battles;
DROP FUNCTION IF EXISTS fn_actualizar_stats_batalla();

CREATE FUNCTION fn_actualizar_stats_batalla() RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO player_stats (
        user_id, battles_played, battles_won, battles_lost,
        current_streak, longest_streak, updated_at
    )
    VALUES (
        NEW.user_id,
        1,
        CASE WHEN NEW.result = 'victoria' THEN 1 ELSE 0 END,
        CASE WHEN NEW.result = 'derrota' THEN 1 ELSE 0 END,
        CASE WHEN NEW.result = 'victoria' THEN 1 ELSE 0 END,
        CASE WHEN NEW.result = 'victoria' THEN 1 ELSE 0 END,
        now()
    )
    ON CONFLICT (user_id) DO UPDATE SET
        battles_played = player_stats.battles_played + 1,
        battles_won    = player_stats.battles_won
                            + CASE WHEN NEW.result = 'victoria' THEN 1 ELSE 0 END,
        battles_lost   = player_stats.battles_lost
                            + CASE WHEN NEW.result = 'derrota' THEN 1 ELSE 0 END,
        current_streak = CASE
                            WHEN NEW.result = 'victoria' THEN player_stats.current_streak + 1
                            ELSE 0
                         END,
        longest_streak = GREATEST(
                            player_stats.longest_streak,
                            CASE
                                WHEN NEW.result = 'victoria' THEN player_stats.current_streak + 1
                                ELSE player_stats.current_streak
                            END
                         ),
        updated_at     = now();

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_stats_batalla
AFTER INSERT ON battles
FOR EACH ROW
EXECUTE FUNCTION fn_actualizar_stats_batalla();
Por qué existe: las estadísticas son un dato derivado del historial. El trigger las mantiene automática y atómicamente — battles_played = won + lost nunca se desincroniza. El INSERT ... ON CONFLICT crea la fila la primera vez y la actualiza después.

07 — Defensa

Preguntas probables de la defensa

PreguntaRespuesta corta
¿ACID y CAP no chocan?No: ACID es la semántica dentro del nodo; CAP es el trade-off entre nodos cuando hay partición. PG da ACID local y es CP en distribución.
¿Por qué CALL y no una función?Es un procedimiento almacenado como pide el enunciado; además podría hacer su propio COMMIT. Ojo: CALL no acepta subconsultas → variables \gset.
¿Por qué el trigger solo calcula stats y no gemas?Separación de responsabilidades: el trigger refleja datos derivados automáticamente; pagar gemas es negocio con validación y transacción explícita → procedimiento.
¿Y si el backend cae, pierdo lo escrito?No: synchronous_commit = on + WAL; el COMMIT confirmado es durable.
¿sync({alter:true}) no rompe el esquema?Puede quitar los DEFAULT now(); por eso schema.sql los restaura (sección 8 de TABLAS.md) y los procedimientos escriben fechas explícitas.
¿Cuántos datos hay?10 tablas, 1 vista, 1 procedimiento, 1 trigger, 77 restricciones; demo: 4 usuarios, 18 batallas, 18 cartas, 10 misiones.
08 — Conclusiones

Resumen y conclusiones

¿Qué hace la BD?

Persiste con integridad todo el estado que va más allá de la partida: identidad, credenciales bcrypt, stats derivadas, historial, catálogos y progreso.

¿Cómo se relaciona?

La vista lee con JOIN (no escribe), el procedimiento escribe en transacción, el trigger sincroniza stats, y las FK CASCADE limpian el progreso al borrar un usuario.

¿Qué garantiza?

Integridad (77 restricciones), ACID completo, CP ante caídas, derivación automática (trigger) e idempotencia de los scripts.
