ACID & CAP Cada garantía demostrada con el código real del backend.

Esta página no explica la teoría en el aire: toma el código que corre hoy en Elemental Universe y muestra dónde vive cada propiedad de transacción (ACID) y cómo el backend elige su camino dentro del teorema CAP. Cada bloque incluye el fragmento exacto, qué hace y por qué satisface la garantía.

00 / CONTEXTO

Dos preguntas distintas

ACID protege una transacción. CAP describe qué cedes cuando la red se parte.

ACID es un conjunto de propiedades que garantizan que una operación sobre la base de datos se ejecute como una unidad confiable: o pasa completa y correcta, o no pasa. Aplica dentro de un solo nodo y lo imponen el motor (SQLite/PostgreSQL) más las decisiones del código.

CAP es un teorema para sistemas distribuidos: ante una partición de red no puedes tener a la vez consistencia fuerte y disponibilidad. Solo importa cuando hay varios nodos comunicándose. Este backend elige ese reparto de forma explícita según el subsistema.

01–04 / ACID

Atomicidad · Consistencia · Aislamiento · Durabilidad

Cada letra, el archivo exacto, y por qué el código la cumple.

A
Atomicidad · todo o nada

La operación no deja estados a medias

Una transacción se ejecuta completa o se revierte; nunca queda un resultado parcial en la base de datos.

DatabaseInitializer.sync()

Qué hace

Antes de sincronizar el esquema captura y elimina las vistas, ejecuta el sync y las vuelve a crear.

Por qué cumple Atomicidad

El bloque try / finally garantiza que restore() se ejecute incluso si sync() lanza un error. El par capturar→restaurar funciona como una unidad indivisible: el sistema nunca se queda con las vistas caídas y el esquema a medio actualizar.

Segundo respaldo

findOrCreate() de Sequelize (usado en logros y cartas) es una única sentencia atómica: inserta o devuelve el existente, sin ventana para duplicados.

C
Consistencia · reglas nunca violadas

Los invariantes siempre se respetan

Toda transacción lleva la base de un estado válido a otro estado válido: no se permite un username o email repetido.

AuthService.register() · L27–L33

Qué hace

Antes de crear el usuario el servicio consulta si el correo ya existe y lanza un ConflictError; además el modelo declara unique sobre username y email.

Por qué cumple Consistencia

Hay doble barrera: la lógica de aplicación evita el caso común, y el UNIQUE del motor es la garantía dura — aunque dos registros simultáneos pasaran la primera validación, la base rechaza el segundo. El invariante "email único" nunca se rompe.

Refuerzo del dominio

Los comentarios del proyecto confirman que las estadísticas se derivan de un trigger de PostgreSQL al insertar la batalla, evitando que dos escritores dejen contadores contradictorios.

I
Aislamiento · sin interferencias

Las operaciones concurrentes no se pisan

Dos operaciones simultáneas no ven estados intermedios de la otra ni corrompen el mismo registro.

RoomManager.createRoom() · L17–L22

Qué hace

Se escribe con upsert (una sola sentencia atómica) y el generador de códigos repite hasta encontrar uno libre.

Por qué cumple Aislamiento

upsert reemplaza el patrón leer-modificar-escribir, eliminando la race condition: no hay instante entre la lectura y la escritura donde otra operación pueda colarse. El motor serializa la escritura (SQLite bloquea escritores; PostgreSQL usa MVCC).

Mismo patrón en salas

El do/while que prueba códigos solo acepta uno que no exista todavía, de modo que dos hosts no pueden recibir el mismo código de sala.

D
Durabilidad · sobrevive al reinicio

Lo confirmado no se pierde

Una vez que la transacción hace commit, el dato permanece aunque el proceso caiga o el servidor se reinicie.

DatabaseFactory.build() + models

Qué hace

El dialecto SQLite apunta a un archivo en disco; en producción el mismo factory crea un Sequelize postgres con SSL opcional.

Por qué cumple Durabilidad

Los commits se escriben en database.sqlite (o en el volumen de PostgreSQL), no en memoria: sobreviven al ctrl+C o a un crash. Los modelos usan timestamps: true, que además deja rastro auditable de createdAt/updatedAt.

05 / CAP

El reparto bajo partición

Este backend no es un clúster: elige según el subsistema.

El teorema CAP dice que un sistema distribuido solo puede garantizar dos de estas tres propiedades a la vez cuando la red se divide (partition). No se elige libremente: cuando hay partición, estás obligado a elegir entre seguir respondiendo (A) o devolver siempre el dato correcto (C).

Aquí el diseño separa los datos de cuenta (consistentes y durables) del estado de las partidas (disponible, efímero).

C / CONSISTENCY

Consistencia

Toda lectura ve la última escritura confirmada. En este backend lo aportan las restricciones únicas y los triggers de la base de datos.

A / AVAILABILITY

Disponibilidad

Toda petición recibe respuesta (sin error), aunque la red falle. Lo aportan los sockets en memoria que nunca dejan de atender eventos.

P / PARTITION

Tolerancia a partición

El sistema sigue operando aunque se pierdan mensajes entre nodos. La elección real depende del despliegue (¿un solo nodo o varios con réplicas?).

Datos de cuenta

Persistidos con Sequelize (SQLite/PostgreSQL) con UNIQUE y triggers. Prioriza la corrección del dato.

  • ✔ Escribe en disco → garantías ACID completas.
  • ✘ En SQLite es un único nodo: no hay partición de red real → es CA. Con PostgreSQL replicado pasa a CP.

APdisponibilidad + tolerancia a partición

Estado de las partidas

  • ✔ Las salas viven en un objeto en memoria: responden siempre y rápido.
  • ✘ Se pierden al reiniciar el servidor (estado efímero, sin DUrabilidad).
  • ✘ Sin replicación: cada nodo tendría su propia verdad → sin consistencia global.
06 / CONCLUSIÓN

Veredicto

ACID vive en la base de datos; CAP se decide por subsistema.

ACID se cumple íntegramente en la capa de persistencia: atomicidad con try/finally y operaciones atómicas, consistencia con UNIQUE + validación + triggers, aislamiento con upsert/findOrCreate y el motor, y durabilidad por el archivo en disco o PostgreSQL.

CAP no es una sola decisión: el backend elige CP/CA para las cuentas (correcto antes que disponible) y AP para las salas de juego (disponible antes que consistente o durable). Esa división es intencional y coherente: perder una sala efímera es aceptable; corromper una cuenta, no.
